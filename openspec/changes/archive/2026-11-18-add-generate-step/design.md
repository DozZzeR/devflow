# Design: generate step for derived files

## Context

- `src/stages.ts` `runNextStage` / `case "implement"` records `implement ok` right after the model run. Nothing runs between implement and the gates.
- `src/gates.ts` `runCommand(ctx, command, cwd, label)` is the shell runner for the test command and setup. It writes a task log, passes `ctx.parentEnv ?? process.env`, and applies `ctx.config.test.timeout_seconds` through `launchShell` (with process-tree termination). The task's phrase "same env allowlist and timeout handling as the test command" therefore means: call `runCommand`.
- `gateConfig(root, base, workingConfig)` returns the config committed at the task base. The gates and verify already use it, so a role cannot change the commands that devflow runs.
- `rollbackGate` applies test paths (step 2) and then production paths (step 3) with `applyPaths`, optionally re-running setup before step 3. `runVerify` applies the change set, removes `.devflow` and `design.md` from the copy, then runs optional setup.
- Gate-failure feedback: `saveGatesFailure` writes `gates-failure.md` (non-passing gates plus an 80-line log tail), and `reworkFeedback` adds it to the next implement prompt while the last `gates` history entry is not a pass.
- `zoneGate` checks the change set against `task.zone` and the task's own plan folder.
- `test/plugins.test.ts` compares a fresh `build:plugins` output with the committed `plugins/**`.
- `src/glob.ts` `globToRegExp` strips only one leading `./` (`replace(/^\.\//, "")`). `matchesAny` is shared by `src/zone.ts`, `src/hook.ts` and `src/gates.ts`.
- State of the previous attempt: the implementation exists. The schema holes and the weak rollback and retry tests from the earlier round are fixed, and the verify verdict confirmed them. The latest verify verdict was REWORK with one high finding: `src/config.ts` accepts `././plugins/**` (validation strips every leading `./`), but `globToRegExp` strips only one, so the matcher keeps a literal `./` and the zone gate rejects `plugins/x/index.js`. This revision fixes that mismatch; the rest of the design is unchanged.

## Decisions

1. **Schema.** Add `build: z.strictObject({ generate: z.string().min(1).optional(), outputs: z.array(glob).optional() }).optional()` to `ConfigSchema`. `outputs` has **no default**, so the refinement can see whether it was supplied: a `superRefine` on the section adds an issue at path `["generate"]` (reported as `build.generate`) whenever `outputs !== undefined` and `generate` is absent. This rejects `"outputs": []` too. Consumers read `build?.outputs ?? []`. Each glob is checked by a helper `outputGlobProblem(glob)`: first strip every leading `./` segment (`glob.replace(/^(?:\.\/)+/, "")`), then reject when the rest is empty, starts with `/`, starts with a drive letter (`^[A-Za-z]:`), contains `\`, has a `..` segment, or **starts with the string `.devflow`** (plain `startsWith`, no segment boundary, so `.devflow-cache/**`, `.devflow*/**` and `./.devflow/x` are all rejected). Issues on globs are reported as `build.outputs`. `build: {}` stays valid and is a no-op. `DEFAULT_CONFIG` and `devflow init` stay unchanged: no `build` section is written.
2. **Trusted config everywhere.** The implement stage resolves `gateConfig(root, task.base, config).config.build` (falling back to the working config exactly as `gateConfig` does). The command, the outputs used by the zone gate, and the commands used in rollback and verify therefore all come from the same trusted source as `test.command`. One consequence: in this repository the new setting takes effect for tasks whose base commit contains it, not for this task itself.
3. **Generate helper.** `export async function runGenerate(ctx: GateContext, cwd: string, label: string): Promise<TestRun | undefined>` in `src/gates.ts`. It returns `undefined` when `ctx.config.build?.generate` is unset; otherwise it returns `runCommand(ctx, generate, cwd, label)`. Success means `exitCode === 0 && !timedOut`. No new environment handling and no separate timeout setting. Labels: `generate` (implement), `gate_rollback_generate`, `verify_generate`.
4. **Implement ordering.** In `case "implement"`, only when `r.ok` and no `blocked` or `plan_conflict` was parsed: run `runGenerate` with cwd `root`, using a `GateContext` built from the trusted config and `io.env`. On success, record `implement ok` as today. On failure, write `generate-failure.md` and record `{ kind: "complete", stage: "implement", outcome: "fail" }`. The report is `fail` with reason `generate_failed` and details `{ exitCode, timedOut, log }`. The lifecycle needs no change: an implement `fail` already counts an attempt and routes back to implement, or to HUMAN at the limit.
5. **Feedback file.** `GENERATE_FAILURE = "generate-failure.md"` next to `GATES_FAILURE`. Content: `Generate step: fail (generate_failed)`, the command, `exit <code>` or `timed out`, then `Log tail:` and `tail(log, LOG_TAIL_LINES)`. `reworkFeedback` adds `block("Generate step failure on the previous attempt (make the generate command succeed)", …)` when the file exists. The implement case removes the file right after composing its context and before launching the model (the feedback is delivered once), and also removes it on a generate success. The gate-failure path stays untouched.
6. **Zone.** Effective zone = `task.zone` ∪ trusted `build.outputs`, computed in `zoneGate` only when `task.zone` is non-empty. A task with no zone keeps today's `no_zone` behaviour. `task.zone` itself is not rewritten. The implement prompt's "Impact zone" block appends `- <glob> (generated by \`<command>\`; do not edit by hand)` for each output. The implementer's write list stays `zone + tasks.md`.
6a. **One normalization rule for validation and matching.** `globToRegExp` in `src/glob.ts` strips every leading `./` segment, with the same expression the validator uses: `.replace(/^(?:\.\/)+/, "")` (after the existing `\` → `/` conversion). The fix lives in the matcher, not only in `zoneGate`, so every caller (zone gate, hook, zone helpers) treats `./a`, `././a` and `a` the same, and validation and matching cannot drift apart again. Globs in `build.outputs` are kept as written in the config (no transform), so the loaded config still reports the user's values.
7. **Implementer shell scope.** The `bash` list for implement and small becomes `[config.test.command, generate].filter(Boolean)`, using the trusted generate command.
8. **Rollback.** Inside `rollbackGate`: after `applyPaths(..., tests)`, call `runGenerate` (cwd `wt.projectDir`, label `gate_rollback_generate`) before the step 2 test run. After `applyPaths(..., prod)` and the optional setup re-run, call it again before step 3. A non-success returns `blocked("rollback", "generate_failed", started, { logs })`. The baseline is not regenerated. The existing `finally` (worktree removal) and the working-tree status comparison are unchanged.
9. **Verify.** In `runVerify`, after the setup block and before the verifier: `if (!failure)`, run `runGenerate` with cwd `wt.projectDir` and label `verify_generate`. Its failure sets `failure = "verify_generate_failed"`, which records `verify human` through the existing path.
10. **Repository config and bundles.** `"build": { "generate": "npm run build:plugins", "outputs": ["plugins/**"] }` in `.devflow/config.json`. Because this change edits `src`, the implementer runs `npm run build:plugins` and commits the rebuilt `plugins/**`; otherwise `test/plugins.test.ts` fails.
11. **Docs.** A README sentence in the settings paragraph describes `build.generate` / `build.outputs`, when they run, and that `build.outputs` requires `build.generate`.

Rejected: normalizing `./` only inside `zoneGate` or with a `transform` in the schema; the first leaves other `matchesAny` callers inconsistent, the second changes the values the loaded config reports. Rejected: keeping `.default([])` on `outputs` and detecting presence with a preprocess step; dropping the default is simpler and makes "supplied" visible to the refinement. Rejected: a segment-boundary `.devflow` check; any glob that starts with `.devflow` can match devflow state or confuse readers, so a plain prefix check is the rule. Rejected: rewriting `task.zone` when a design is approved, and writing generate failures into `gates-failure.md` (reasons unchanged from the earlier version: zone drift, and ambiguous stale-feedback rules).

## Test plan

- **Build settings** (`test/config.test.ts`):
  - Accepted section round-trips; config without `build` parses and has no `build.generate`; `build: {}` parses.
  - Rejected naming `build.outputs`: `../x/**`, `/abs/**`, `C:/x`, `a\\b`, `""`, `./`, `.devflow`, `.devflow/**`, `.devflow-cache/**`, `.devflow*/**`, `./.devflow/runs/**`, `././.devflow-x`.
  - Rejected naming `build.generate`: `{ "outputs": ["plugins/**"] }` **and** `{ "outputs": [] }`.
  - Still accepted: `./plugins/**` and `././plugins/**` with a generate command (the loaded value is reported as written), and `src/.devflow-notes/**` (the prefix rule applies only to the start).
  - `build.watch` rejected as unknown. The repository's `.devflow/config.json` loads and reports `npm run build:plugins` / `plugins/**`.
- **Generate runs after implement** (`test/run.test.ts`): a command-runner implement role plus a `build.generate` node script that appends a marker after the fake implementer's marker → `ok`, `implement ok`, one generate run, after the model, cwd = project root. Variants: model run fails, blocked, plan conflict → no generate marker.
- **Trusted command** (`test/run.test.ts`): base config generate A, working config generate B → only A's marker appears.
- **Failure feeds back** (`test/run.test.ts`): generate prints `bundle error` and exits 1 → `fail`, `generate_failed`, `attempts.implement` incremented, `generate-failure.md` contains `bundle error`. Timeout variant (`test.timeout_seconds: 1`, sleeping script) → `fail`, `generate_failed`, file mentions the timeout.
- **Feedback consumed before the retry runs** (`test/run.test.ts`): the retry's fake implementer script checks `.devflow/runs/<id>/generate-failure.md` when it starts and exits non-zero (or writes a `feedback-still-present` marker that the test asserts is absent) if the file exists. The test also asserts that this attempt's saved prompt contains `bundle error`. After that attempt's successful generate the file is absent, and a third attempt's prompt lacks `bundle error`.
- **Implementer may regenerate** (`test/run.test.ts`): with `build.generate` set, the implement run request's `bash` equals `[test.command, build.generate]`.
- **Outputs join the zone** (`test/gates.test.ts`): zone `src/**`, outputs `plugins/**`, change set `src/a.ts` + `plugins/x/index.js` → pass; without `build` → fail listing `plugins/x/index.js`; medium task without zone but with outputs → `blocked` `no_zone`. **Repeated prefix**: the same fixture with outputs `././plugins/**` (and a variant `./plugins/**`) → pass, `plugins/x/index.js` is not listed; a zone of `././src/**` with outputs `plugins/**` → pass. This case fails against the old one-prefix `globToRegExp`. Prompt listing (`test/run.test.ts`): the saved implement prompt marks `plugins/**` as generated.
- **Rollback worktree regenerates** (`test/gates.test.ts`): fixture where `gen.mjs` **first checks that the changed test file (e.g. `test/value.test.mjs`, added by the change) exists in its cwd and contains a marker such as `// gen-marker`, exiting 1 otherwise**, then writes `out/bundle.txt` from `src/value.txt`; the test checks `out/bundle.txt` equals `src/value.txt`. The change edits `src/value.txt` and adds the marked test but does not touch `out/`. With `build.generate: "node gen.mjs"` the gate passes, which proves step 2 generates only after the test files are applied and step 3 sees a fresh bundle. A log shows generate ran in the worktree (cwd ≠ project root); the user's `out/bundle.txt` and `git status --porcelain` are unchanged. Without `build` the fixture fails `tests_fail_with_change` (stale-bundle comparison kept). A generate script that always exits 1 → `blocked` `generate_failed`, no leftover worktree.
- **Verify copy regenerates** (`test/run.test.ts`): a verify command-runner role writes `VERDICT: PASS` only if `out/bundle.txt` in its cwd matches the applied `src/value.txt` → `verify pass`. Failing generate → `verify human`, `verify_generate_failed`, verifier marker absent.
- **Regression**: existing suites in `test/gates.test.ts`, `test/run.test.ts`, `test/config.test.ts` pass unchanged. `test/plugins.test.ts` passes against the rebuilt `plugins/**`. `npm test` is green. Environment failures seen in the last verify run (esbuild access denied in `test/plugins.test.ts`, `EPERM` cleanup in the quoted-command timeout test, the surviving grandchild in `test/proc.test.ts`) are not caused by this change; the implementer reports them with output if they recur rather than editing files outside the zone.
